# CRM and GOS API coverage audit

Source: public/Feedback/docs/GOS API Copy 2.postman_collection.json. Exactly **42 request examples**, including repeated routes with different bodies and one Firebase password sign-in request; these are not 42 distinct Laravel endpoints.

## Access and execution

Open /dashboard/crm → Pipeline Settings → API QA · 42 requests. All 41 GOS examples have individual executable controls, editable JSON, shared resource IDs, multipart file support, expected rejection handling, request results and an in-session attempt history. Password sign-in links to /login and uses the existing Firebase flow. No Postman scripts or document instructions are executed. No passwords or bearer tokens are stored in the QA catalog.

Run examples individually in collection order against a QA workspace. Set pipelineId to a disposable pipeline, inspect bodies before confirming mutations, and retain externalMessageId for the duplicate-message case. Successful responses populate leadId, sourceId, pipelineId, conversationId and playgroundTestId. Poll Get source until ready before asking AI questions. The server's queue worker and AI configuration must be operational. QA PASS checks expected HTTP status and explicit assertions for health, current user, indexing readiness, playground answers/citations, grading and inbox outcomes (paused, answered, duplicate, handoff). Other response fields remain available for inspection; this does not execute or fully replace every Postman assertion. Expected validation rejections are identified separately. QA does not automatically run destructive requests or send outbound staff messages.

## Persistence and limits

- Laravel owns the documented contact fields, pipeline CRUD supported by the collection, stage moves, notes, imports and bulk actions. Filter/search changes are synchronous local operations with no artificial network delay. The same filtered rows drive Kanban, table and filtered exports.
- Whole-pipeline exports use GET /crm/leads/export with Accept: text/csv and download gos-contacts.csv. Filtered/selected exports use the existing local CSV encoder because the collection only defines pipeline-wide exports.
- Tasks, follow-up dates, qualification, archive state, interest, consent and per-contact follow-up lifecycle have no endpoints in this collection. These controls await tenant-scoped Firestore writes before committing Redux or clearing drafts. They do not send undocumented fields to Laravel. The existing workspace listener still supplies cross-session updates.
- Pipeline Settings contains a confirmation for DELETE /crm/pipelines/:id. **That route is absent from the collection**, so backend availability remains unverified. Errors retain the local pipeline. Nonempty pipelines and the last remaining pipeline cannot be deleted through this control.
- Conversation history loads linked GOS threads and workspace threads; it only associates explicit contact IDs, nonempty email addresses or normalized phone numbers. Customer names alone cannot safely link threads. The supplied inbox ingestion contract does not accept lead_id, so simulated messages without identifying metadata may only appear in the Inbox.
- Appointments and orders/payment records come from existing workspace booking, order and transaction collections; the Postman file contains no booking/order/invoice endpoints. Stored invoice numbers are shown when present.
- AI Automation polls the global assistant status and shows explicitly associated workspace sequences. Per-contact lifecycle/consent preferences are persisted controls, not evidence of message delivery or enrollment in a running sequence.
- Open record details, conversations and assistant status refresh every 10 seconds while mounted. Background reads cancel on unmount; explicit saves disable controls, display a spinner and reject duplicate clicks before React renders.

## Verification

- npm run build (TypeScript and production bundle).
- npm run test:crm (transport, booking-stage fallback, CSV/model and persistence behavior).
- npm run test:crm:browser (requires playwright-core via PLAYWRIGHT_MODULE and installed Edge, or FUNNEL_BROWSER_PATH). Uses mocked API responses and Firestore writes, never real workspace data. Covers portal filter selection, search in both views, CSV header/download/import mapping, task save success/failure, duplicate clicks, follow-up confirmation and all eight record tabs.

**Live authenticated replay has not been performed in this environment.** The audit establishes accessible UI coverage and automated mock verification; final server compatibility, indexing/delivery configuration and visual regression acceptance still require a signed-in QA workspace.
